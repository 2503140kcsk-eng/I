# CFE proof layer: reference semantics v0.2

## Purpose

The CFE layer separates ordinary engine strength from proof trust. YaneuraOu,
dlshogi or another USI-compatible engine may suggest moves and generate proof
candidates. A separate rules adapter verifies a finite proof DAG. An evaluation,
a principal variation, a DFPN proof number or a condition-cube hit is never
itself a proof.

## Implemented reference slice

1. Certificate Extractor converts a labelled solver DAG to a content-addressed
   certificate, then submits it to the verifier.
2. Footprint Matcher identifies exact-state and broader feature-cube candidates.
   It never accepts a proof.
3. Certificate Verifier checks legal checking moves, every defender evasion,
   successor states, terminal mate and history context through a rules adapter.
4. Governor schedules verification before ordinary search and reports when
   verification cannot fit within CPU/GPU/memory/thermal budgets.

The verifier is a reference interface with toy-game tests. It is not yet a
production Shogi rules implementation and does not certify real engine output.

## Certificate semantics

Schema: cfe.shogi.certificate, version 1, objective: tsume-mate.
The ruleset ID and verifier ABI are exact compatibility gates. The certificate
also binds the absolute attacker side. Every verification call must provide an
out-of-band expectedRootState; a certificate verified without an exact root
binding is not eligible for pruning. Nodes are content-addressed with SHA-256
over canonical JSON.

The certificate-level attackerSide ("b" or "w") fixes the attacker's absolute
color. The root state's turn must equal attackerSide. Every call to the
verifier must also supply expectedRootState out-of-band; that value is not
stored inside the proof graph and binds the certificate to the exact requested
search position.

Each proof node contains:

- state: canonical SFEN, absolute side-to-move ("b" or "w"), and a SHA-256
  digest committing to the history context needed for repetition adjudication;
- kind: OR, AND or TERMINAL_MATE;
- edges: sorted USI move plus child-node digest.

For an attacker OR node, one or more legal checking moves must be supplied.
For a defender AND node, the edge set must equal the complete set of legal
evasions independently regenerated by the verifier. A terminal node is valid
only if the rules adapter independently identifies defender checkmate.

The DAG must be finite and acyclic. Every node must be reachable from the root.
Every edge must reproduce the child's exact canonical state, including its
history digest. The verifier rejects missing children, hash mismatches,
unsupported versions, incompatible rulesets, malformed states, omitted
defender evasions and resource-limit violations.

## Why history belongs in the key

Shogi repetition and perpetual-check outcomes depend on the sequence leading
to the current board. A board-only SFEN-derived transposition key is therefore
insufficient for reusing a solved result. historyDigest commits to the history
context used by the rules adapter. A production adapter must specify and test
which history data is required; a digest without the underlying committed data
is not enough for an external auditor to reconstruct a proof. It must also
provide a terminalStatus result with exactly three values: ongoing, checkmate,
or non-mate-terminal. Repetition, perpetual-check adjudication and every other
rule-decided outcome are non-mate-terminal, never a proof leaf.

## Footprint policy

A footprint is an index, not a theorem.

- EXACT_CANDIDATE: the complete root state and history match. The certificate
  must still pass independent verification before use.
- ABSTRACT_CANDIDATE: the feature cube matches, but the root state differs.
  This is only a retrieval hint. The proof cannot be transferred to the new
  position.
- MISS: no compatible candidate is found.

Generalized condition cubes are deliberately untrusted in v0.2. A future
version may add parameterized certificates only after a symbolic verifier
proves that every omitted feature preserves all proof preconditions and the
complete AND/OR quantification.

## Restrictions

- No generalized proof-tree extraction from YaneuraOu is claimed yet.
- No complete shogi legality verifier is included in this slice.
- No evaluation, PV, neural output or unverified DFPN result may prune search
  as a proven fact.
- The reference tests require no network service or paid runtime.

## USI observer boundary

The current USI module is a transport-independent protocol observer. It parses
standard position/go forms, preserves the caller's original command for
pass-through, and tracks search lifecycle and YaneuraOu mate claims. A
`checkmate <PV>` response is explicitly marked `ENGINE_CLAIM_ONLY`; it is not
a proof tree and cannot be accepted as a certificate. The production process
supervisor, engine selection, cancellation and certificate export are future
integration work.


## History commitments and transposition identity

Each state envelope carries a lowercase SHA-256 `historyDigest`, not a
board-only key. The reference history ledger commits to the initial SFEN and
then hash-chains each ply's mover, USI move, resulting SFEN and check flag.
`historyPositionKey` combines ruleset ID, SFEN and that digest. Consequently,
identical boards reached through different histories do not alias in the
solved-evidence cache.

The ledger is an integrity commitment, not a legality proof: the production
rules verifier must replay every move, independently recompute resulting
positions and check flags, and apply the exact repetition/perpetual-check
adjudication of the pinned ruleset. The hash chain alone cannot establish that
the recorded game was legal.


## DFPN implementation comparison

The current source files show a useful division of experimental responsibilities:

- YaneuraOu's Tanuki mate engine uses df-pn with TCA and stores PN/DN search
  metadata. Its source still lists dominance, ProofPieces and SNDA as TODOs.
- cshogi has a separate OSL-based DFPN implementation. Its transposition entries
  include the hand, PN, DN, depth and searched-node count; its lookup code
  explicitly compares hand superiority for solved entries. This is an
  implementation-level baseline for dominance experiments, not a certificate
  export interface.
- mShogi has a Rust df-pn mate core with a proof table and history-sensitive
  rule-score exclusions. Its Shogi proof helper is independently grounded in
  native Shogi rules and pawn-drop-mate legality, but uses bounded proof lines,
  not a reusable complete certificate graph.
- dlshogi's policy/value network and MCTS self-play are training and move-order
  sources. They do not become proof authorities by producing high-confidence
  scores.

CFE therefore keeps PN/DN, PV and neural output as provenance and search
guidance. The certificate verifier reconstructs AND/OR obligations from legal
moves, rather than trusting those summaries.

## Proof-state history witness requirement

A digest is a commitment, not evidence that an event sequence is valid. For
production mode, each proof node must carry the complete history ledger, and
the verifier recomputes its hash chain and checks that its last SFEN equals the
node's declared SFEN. The rules adapter must additionally replay every move
and independently confirm legality, gave-check annotations, repetition and
perpetual-check adjudication. Synthetic tests can opt into opaque history only
with the explicit `allowOpaqueHistory: true` test adapter flag; production
adapters must leave that flag absent.


## nozaq/shogi-rs SFEN replay audit

The source inspection found a concrete history-replay concern. During
`set_sfen(... moves ...)`, each successful `make_move` is followed by another
`log_position`, although the normal/drop move routines already logged before
running repetition detection. If repetition returns an error, the bulk loader
breaks and returns success; the move routine has changed the board/ply but
has not pushed its move record. The pinned Rust probe under
`tools/shogi-rs-audit` compares direct replay with bulk replay to reproduce
the observed history truncation. Until the probe is green and this behavior is
understood or fixed, the crate is a candidate only, not a trusted verifier
history loader.


## Condition-cube inclusion semantics

A condition cube is a conjunction of feature equalities. For example,
`phase=middlegame ∧ attacker=b` is stronger (more specific) than
`phase=middlegame`, because every assignment satisfying the first also
satisfies the second. `compareConditionCubes` returns:

- `LEFT_STRONGER` or `RIGHT_STRONGER` when one cube implies the other;
- `EQUIVALENT` when both imply each other;
- `INCOMPARABLE` when the cubes overlap but neither implies the other;
- `DISJOINT` when a shared feature has contradictory values.

`compareFootprints` first requires identical ruleset, verifier ABI and
attacker side. It reports condition inclusion and exact-root equality for
indexing/eviction heuristics only. Every result has
`proofTransferAllowed: false`: symbolic proof-preserving generalization is
not implemented, and a cube relationship never transfers a mate theorem.


## Certificate Extractor -> Footprint pipeline

After (and only after) the certificate passes the independent verifier, the
Extractor computes a structural proof summary and creates a footprint. A
rules adapter may optionally expose a deterministic
`deriveFootprintFeatures(position, canonicalRootState)` function together
with a stable `footprintFeatureAbi`. The callback returns flat scalar feature
values, which become a conjunction of equality literals (the condition cube).
If no feature extractor is registered, the Extractor still returns an
exact-root-only footprint with an empty cube.

The feature ABI identifies the meaning and extraction rules for every literal.
Abstract lookup is rejected unless the query declares the exact same feature
ABI. The proof summary records OR/AND/terminal counts, edges, depth and
branching factors; it is metadata for indexing and Governor heuristics, not an
additional proof.

**Safety boundary:** a cube match on a different root is always only an
`ABSTRACT_CANDIDATE`. The certificate must be verified against the actual
query root, and the current verifier rejects a different root. No proof
transfer, pruning or result reuse across different root states is implemented.
